# よくある質問 { #frequently-asked-questions }

> このページは AP2 ドキュメントの非公式日本語訳です。
> [英語の原文を読む](https://github.com/google-agentic-commerce/AP2/blob/main/docs/faq.md)

1. 現在、このプロトコルで何ができますか？

    - AP2 のコアとなる Python ライブラリを使ったサンプルエージェントで、さまざまな買い物の流れを試せます。
      エージェントを起動し、好きな商品を探してみてください。
      サンプルは実際の決済サービス事業者を模擬するため、外部サービスに依存せずに試せます。
      エージェントの処理中に Mandate がどのように使われるかを確認してください。
      今後もサンプルや SDK を公開する予定です。アイデアも歓迎します。
      サンプルコードを使って、複数の AI エージェント間の支払いを実装したり、プロトコルを拡張して新しい決済シナリオを試したりできます。
      たとえば、支払い方法や認証方法を変更できます。

1. サンプルをひな型にして、各役割のエージェントを自作できますか？

    - はい。[定義済みの役割](ap2/implementation_considerations.md)のどれでも実装できます。
      Google Cloud の [ADK](https://google.github.io/adk-docs/) や [Agent Builder](https://cloud.google.com/products/agent-builder) のほか、任意のエージェント開発プラットフォームを使えます。

1. 自作のエージェントをこのプロトコルに参加させられますか？

    - はい。[定義済みの役割](ap2/implementation_considerations.md)のどれでも、自作のエージェントで担えます。
      LangGraph、AG2、CrewAI などのフレームワークや、ランタイムの種類にかかわらず、AP2 を実装できます。

1. 実際に支払わずに試せますか？

    - 実際の資金移動を伴わない模擬の支払い方法を利用できる社内環境があれば、その環境で試せます。

1. 利用したいフレームワークに対応する MCP サーバーや SDK はありますか？

    - 現在、決済サービス事業者と協力して SDK と MCP サーバーを開発しています。
      最新情報は今後の更新をご確認ください。

1. 暗号資産決済の x402 標準に対応していますか？

    - AP2 は特定の支払い方法に依存しないよう設計されており、さまざまな決済システムで安全にエージェントコマースを実現できます。
      エージェントがクレジットカードを使う場合も、ステーブルコインで取引する場合も、安全で監査可能な仕組みを提供します。
      この設計により、新しいエコシステムにも同じ原則を適用し、取引の信頼性を共通の基準で確保できます。

      最初の例として、A2A と x402 を組み合わせた実装 [google-agentic-commerce/a2a-x402](https://github.com/google-agentic-commerce/a2a-x402/) を参照してください。
      今後はこの実装と AP2 の整合性を高め、ステーブルコインを含むさまざまな支払い方法を組み合わせた解決策を構築しやすくします。

1. Verifiable Credential（検証可能な資格情報）とは何ですか？

    - Checkout Mandate や Payment Mandate のように、暗号技術で保護された標準化済みのデータオブジェクトです。
      取引を構成する要素として暗号学的に署名され、改ざんを検知でき、署名者による後からの否認を防ぎます。

1. プロトコルはユーザーの主導権とプライバシーをどう確保しますか？

    - 最終的な決定権は常にユーザーにあり、ユーザーは自分のエージェントの行動を細かく制御できます。
      ペイロードの暗号化と選択的開示で開示データを最小限に抑え、Shopping Agent が機密性の高い PCI データや個人を特定できる情報（PII）にアクセスできないようにします。
      これにより、会話で入力したプロンプトや個人の支払い情報などを保護します。

1. AP2 は取引の責任の所在をどのように明確にしますか？

    - AP2 の主な目的の一つは、決済ネットワークが責任の所在や損失負担の原則を定める際に使える証拠を提供することです。
      紛争が起きた場合、カードネットワークなどの裁定者は、ユーザーが署名した Checkout Mandate でエージェントと消費者の取り決めを確認し、争点となっている取引の詳細と照合できます。
      この照合は、取引の責任の所在を判断する材料になります。

1. エージェントのハルシネーションによる誤購入をどう防ぎますか？

    - AP2 は、取引の根拠として、関係するすべての当事者から、検証可能で否認できない確定的な意思の証明を求めます。
      たとえば、ユーザーが署名した Checkout Mandate がこれに当たります。
      言語モデルの確率的で曖昧な出力から意思を推定する場合に生じる誤購入のリスクに対処できます。

1. なぜ当初から暗号資産と Web3 に対応したのですか？

    - デジタル決済を含む幅広い支払い方法に対応することで、今後登場する決済方法にも適応できるようにしています。
      Coinbase、Ethereum Foundation、MetaMask などのパートナーとの協業は AP2 の柔軟性を実証し、従来の経済圏と Web3 の経済圏をつなぐことで、マイクロペイメントなどの新しい用途を可能にします。

1. プロジェクトに参加するにはどうすればよいですか？

    - AP2 は、A2A プロトコルと同様に Google が立ち上げたオープンソースプロジェクトです。
      GitHub での議論、不具合報告、機能要望、プルリクエストを歓迎します。
      新しいサンプル、連携機能、SDK を共同で開発しており、AP2 チームへの連絡には GitHub が適しています。

1. UCP と AP2 はどう違いますか？ エージェントによるチェックアウト機能とはどう関係しますか？

    - **AP2**：エージェントが安全に取引し、責任の所在を明確にするための共通プロトコルです。
      Universal Commerce Protocol が購入プロセス全体を調整し、AP2 は取引の認可と署名に特化した決済レイヤーを提供します。
      今後、ユーザーが AI エージェントに購入を委任し、エージェントが取引を進めるようになると、このフローで AP2 が重要になります。
      このモジュール構成により、柔軟性を保ちつつ、購入者、販売者、サービス事業者の間で取引の信頼性を確保できます。
      販売者は、AI エージェントが主導する取引向けに、UCP の拡張として AP2 を組み込めるようになります。

    - **エージェントによるチェックアウト（agentic checkout）**：この機能は、ユーザーの指示に従って店舗のウェブサイトで購入を代行します。
      UCP を利用すると、ユーザーは AI Mode や Gemini 上で直接購入できます。
      これらの画面上で購入すると、ユーザーはいずれの場合も販売者と直接つながり、注文状況の通知など、購入後に必要な情報を受け取れます。
      ポイントの利用や、過去のカートからの購入にも今後対応する予定です。

1. どのような場合に AP2 を使えばよいですか？

    - 販売者が AI Mode や Gemini などの Google の AI インターフェースで商品を紹介し、その場でチェックアウトを完了できるようにする場合は、Universal Commerce Protocol を使用します。
      ユーザーの不在時に AI エージェントが自律的に購入するシナリオでは、AP2 を拡張として追加できます。

    - Google の商品検索インターフェース以外で、AI エージェント同士の支払いフローを実装したい場合や、自社の商品検索インターフェースと AI エージェント間の支払いフローに Verifiable Credential を組み込みたい場合も、AP2 を利用できます。

1. AP2 の今後の予定は何ですか？

    - コア仕様の策定は [FIDO](https://blog.google/products-and-platforms/platforms/google-pay/agent-payments-protocol-fido-alliance/) で継続し、エージェントが関与するあらゆる支払いに使える、オープンで相互運用可能なプロトコルとして発展させます。
    - サンプルコードと SDK も引き続き改善し、AP2 仕様の最新技術を取り入れた実装を提供します。
