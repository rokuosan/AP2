# 概要 { #executive-summary }

> このページは AP2 ドキュメントの非公式日本語訳です。
> [英語の原文を読む](https://github.com/google-agentic-commerce/AP2/blob/main/docs/overview.md)

AI エージェントがデジタルコマースに加わると、利便性が高まり、利用者ごとの要望に応えやすくなり、取引の手間も減ると期待されています。
一方、既存の決済インフラは、自律的なエージェントがユーザーに代わって取引したり、エージェント同士で取引したりすることを想定していません。
現在の決済プロトコルは、人が信頼できるインターフェースを直接操作することを前提としているため、エージェントの真正性や取引権限を安全に検証する仕組みを備えていません。
取引に伴う責任の所在が曖昧なままでは、エージェントコマースの普及が妨げられます。

信頼できる共通のプロトコルがなければ、互換性のない独自の仕組みが乱立し、エコシステムが分断され、安全性も損なわれるおそれがあります。
販売者の対応は複雑になり、ユーザーの手間は増え、金融機関は統一した基準でリスクを評価できません。
AP2 は、この課題に対処するためのオープンで相互運用可能なエージェント決済プロトコルです。
Agent2Agent（A2A）、Model Context Protocol（MCP）、Universal Commerce Protocol（UCP）の拡張として、AI が関わる取引を安全かつ確実に進めるための枠組みを提供します。

## エージェント決済に共通のプロトコルが必要な理由 { #the-new-frontier-of-commerce-why-agent-payments-require-a-foundational }

### 1.1 エージェントコマースの広がり { #11-the-rise-of-agent-commerce }

デジタルサービスの利用方法は、ユーザーが画面を直接操作する形から、会話で指示を出し、タスクの実行を委任する形へと広がっています。
AI エージェントは複雑な依頼を理解し、複数の手順を自律的に実行する役割を担いつつあります。
商取引では、日常の購入やサブスクリプション管理に加え、商品の比較調査、価格交渉、複数の販売者への注文を状況に応じてまとめる作業も委任できます。
ユーザーは自分の要望に合った商品を手間なく購入でき、販売者は顧客に商品やサービスを届ける新しいチャネルを得られます。

### 1.2 エージェントへの信頼と取引責任 { #12-the-foundational-gap-a-crisis-of-trust-and-liability }

現在の決済プロトコルは、人が販売者のウェブサイトや決済事業者のアプリなど、信頼できるインターフェースを直接操作することを前提としています。
認証、認可、責任の判断は、いずれもその操作を前提にしています。

自律的なエージェントが支払いを開始する場合、既存の仕組みでは、次の問いに十分に答えられません。

* **認可と監査可能性**：特定の購入を行う権限をユーザーがエージェントに与えたことを、どのような証拠で検証できるでしょうか。
* **意思の真正性**：エージェントの要求がユーザー本人の意思を正確に反映していることを、販売者や決済処理事業者はどう確認できるでしょうか。
* **エージェントの誤りとハルシネーション**：依頼の解釈を誤ったり、実在しない商品情報を生成したりした場合、誤購入をどう防ぐのでしょうか。
* **責任の所在**：不正取引や誤った取引が起きた場合、責任は、委任したユーザー、Shopping Agent の開発者、注文を受けた販売者、処理した決済ネットワーク、決済サービス事業者（PSP）、オーケストレーション層のどこにあるのでしょうか。

エージェントの権限を検証し、責任の所在を明確にする枠組みがなければ、金融機関はエージェントが開始した取引の承認に慎重になる可能性があります。
販売者は許容できない水準の不正リスクにさらされ、ユーザーも支払い権限をエージェントに委任しにくくなります。

### 1.3 エコシステムが分断されるリスク { #13-the-risk-of-a-fragmented-ecosystem }

広く採用される共通プロトコルがなければ、業界は閉じた独自の仕組みが混在する方向へ進みます。
大手小売業者は特定のエージェント向けに個別の連携を開発し、決済事業者は他社と相互運用できないエコシステムを作るかもしれません。
こうした分断は、参加者に次の影響を及ぼします。

* **ユーザー**：使い慣れたエージェントが一部の販売者や支払い方法にしか対応せず、一貫した手順で購入できなくなります。
* **販売者**：標準化されていない複数の決済連携に対応する開発費と保守費がかかり、中小事業者にとって参入障壁になります。
* **決済エコシステム**：エージェントによる取引全体で共通のリスク指標を収集できなくなります。
  不正対策を一貫して適用できず、コストの増加や取引承認率の低下につながります。

オープンで相互運用可能なプロトコルは、参加者が共通の方法で取引情報を扱えるようにします。
従来は共有できなかった取引情報を共有でき、準拠するエージェントは準拠するどの販売者とも安全に取引できます。
販売者や開発者は、この共通基盤の上でサービスや機能を競えます。

## 2. エージェントコマースの設計原則 { #section-2-guiding-principles-for-a-trusted-agent-economy }

AP2 は、参加者が安全かつ公正に利用し続けられる決済エコシステムを目指しています。
次の原則は、後述するアーキテクチャの設計にも反映されています。

### 2.1 オープン性と相互運用性 { #21-openness-and-interoperability }

AP2 は、既存および今後の A2A、MCP、UCP に向けた、特定の事業者に依存しないオープンな拡張として提案されています。
決済エコシステムのどの参加者でも採用できる、相互運用可能な共通の決済レイヤーを提供します。
開発者はエージェントの新機能を開発でき、販売者は幅広い顧客にアクセスでき、ユーザーは要望に合ったエージェントとサービスを組み合わせられます。

### 2.2 ユーザーの主導権とプライバシー保護 { #22-user-control-and-privacy-by-design }

最終的な決定権は常にユーザーが持ちます。
プロトコルは、ユーザーがエージェントの操作を把握し、細かく制御できるように設計されています。

プライバシーも設計段階から組み込んでいます。
保護の対象には、会話で入力したプロンプト、購入品、支払い情報などが含まれます。
Selective Disclosure（選択的開示）により、買い物に関わるエージェントは機密性の高い PCI データにアクセスできず、専門の事業者と決済インフラの安全な構成要素だけがそのデータを扱います。
開示を最小限に抑えることで、各主体には役割を果たすために必要な情報だけが届きます。

### 2.3 検証可能な意思 { #23-verifiable-intent-not-inferred-action }

大規模言語モデルの出力は確率的で曖昧なため、その解釈だけを取引の根拠にすることはできません。
取引の根拠には、関係するすべての当事者の意思を示す、確定的で否認できない証拠が必要です。
この原則により、エージェントのハルシネーションや誤解釈のリスクに対処します。

### 2.4 取引責任の明確化 { #24-clear-transaction-accountability }

エージェントコマースを決済エコシステムに取り入れるには、取引の責任の所在を明確にする必要があります。
このプロトコルの主な目的の一つは、決済ネットワークが責任の所在と損失負担の原則を定める際に使える証拠を提供することです。
責任の所在を明確にできれば、販売者、Issuer、決済ネットワークが信頼して参加できるようになります。

## 3. 安全な取引を支える役割別のアーキテクチャ { #section-3-architectural-overview-a-role-based-ecosystem-for-secure }

AP2 は、安全性と相互運用性を確保し、責任の所在を明確にするため、参加者の役割ごとに責務を定義します。
責務を分けることで、安全性が高まり、システムの連携も容易になります。

主な役割は次のとおりです。

* **Shopping Agent（SA）**：商品の検索からチェックアウトの組み立て、購入の実行までを担うエージェント。
* **Credential Provider（CP）**：購入に使う Payment Credential を提供する主体。
  エージェントに Payment Credential へのアクセスが認められていることを検証し、その Payment Credential の利用範囲を適切に制限します。
* **Merchant（M）**：Checkout を提供する販売者。
  商品カタログを管理し、注文の商品やサービスを提供します。
* **Merchant Payment Processor（MPP）**：購入に伴う決済を処理する主体。
  対象の Checkout への支払いに Payment Credential を使うことが認可されているかを検証します。
* **Trusted Surface（TS）**：ユーザーが内容を理解したうえで Intent に同意できるようにする、信頼できる UI。
  ユーザーが署名した Mandate を作成する前に同意を得ます。
* **Network and Issuer**：決済ネットワークの提供者と、ユーザーに Payment Credential を発行する主体。
  AI エージェントによる取引専用のトークンの発行にあたり、Credential Provider は決済ネットワークと連携する場合があります。
  Merchant や PSP は、決済ネットワーク経由で Issuer に取引の承認を求めることができます。

以下は、実装を拘束しない役割の組み合わせの例です。

* Shopping Agent の提供者が、エージェントを介さない Trusted Surface を自社アプリ内に設ける。
* Shopping Agent が自前の Credential Provider を提供する。
* Merchant が自前の Merchant Payment Processor を提供する。
* Merchant が Credential Provider を兼ねる。

## 4. 代表的な取引フロー { #section-4-core-user-journeys }

### 4.1 ユーザーが参加する取引 { #41-human-present-transaction }

ユーザーは、買い物などの支払いを伴うタスクを AI エージェントに委任し、支払いの認可が必要になった時点で自分で対応できる状態にいます。
次は代表的な取引フローの一例です。

* **セットアップ**：ユーザーは、利用したい Shopping Agent を、対応する Credential Provider に接続できます。
  接続時に、Credential Provider のインターフェースでユーザーの本人認証が必要な場合があります。
* **商品検索と条件交渉**：ユーザーは、自分が選んだ AI エージェントに買い物を依頼します。
  AI エージェントは、買い物に特化した Shopping Agent にタスクを任せる場合があります。
  Shopping Agent は、1 つ以上の Merchant とやり取りし、ユーザーの希望に合う商品をカートにまとめます。
  Merchant が、Shopping Agent との連携を通じて、会員特典、割引、関連商品、上位商品の情報を提供する場合は、Shopping Agent がユーザーに提示します。
* **Merchant によるカートの確認**：ユーザーは、1 つ以上の SKU の購入を認可します。
  Shopping Agent は、その内容を Merchant に伝え、注文の作成を依頼します。
  Merchant は、カートの内容どおりに商品やサービスを提供することを示すため、ユーザー向けに作成したカートに署名する必要があります。
* **支払い方法の取得**：Shopping Agent は、Credential Provider に支払いの条件を伝え、利用できる支払い方法を参照または暗号化した形で要求できます。
  支払い方法の選択に関係する会員特典や割引（支払いに充当できるカードのポイントなど）も、併せて要求できます。
* **カートの提示**：Shopping Agent が最終的なカートと適用できる支払い方法を Trusted Surface で提示し、ユーザーは認証手続きを経て承認できます。
* **署名と支払い**：ユーザーが署名して承認すると、暗号学的に署名された Checkout Mandate を作成する必要があります。
  Checkout Mandate には、購入する商品とその購入に対するユーザーの確認が明記されます。
  紛争時に Merchant が証拠として使えるよう、Checkout Mandate を Merchant に共有します。
  Payment Mandate は、取引の承認に使うため、別途決済ネットワークや Issuer に共有する場合があります。
* **支払いの実行**：取引を完了するには、Payment Mandate を Credential Provider と Merchant に伝える必要があります。
  たとえば、次の方法があります。
    * Shopping Agent が Credential Provider に、Merchant への支払いの完了を依頼する。
    * Shopping Agent が Merchant に注文を送信し、それをきっかけに決済のオーソリゼーションが始まり、Merchant や PSP が Credential Provider に支払い方法を要求する。
* **Issuer への取引送信**：Merchant または PSP が、その支払い方法を扱う Issuer や決済ネットワークに取引を送ります。
  決済ネットワークや Issuer がエージェントの関与を把握できるよう、取引データにその情報を追加する場合があります。
* **追加認証の要求**：Issuer、Credential Provider、Merchant など、どの参加者も 3DS2 のような既存の仕組みで取引に追加認証を求めることができます。
  追加認証は Trusted Surface でユーザーに提示する必要があります（ホスト型の 3DS など）。
  手続きの完了にあたって、Trusted Surface へのリダイレクトが必要な場合があります。
* **追加認証への応答**：ユーザーは、銀行アプリやウェブサイトなどの Trusted Surface で追加認証を完了できる必要があります。
* **取引の承認**：Issuer が支払いを承認し、成功を通知します。
  Merchant が注文の履行に進めるよう、結果をユーザーと Merchant に伝えます。
  取引結果を確認できる Payment Receipt を Credential Provider に共有します。
  取引が拒否された場合も、必要に応じてその結果を伝えられます。

### 4.2 ユーザーが不在の取引 { #42-human-not-present-transaction }

ユーザーは、買い物などの支払いが必要なタスクを AI エージェントに委任し、自分が不在の間に支払いを進めることを求めます。
デモでは、「SuperShoe の限定スニーカー（ゴールド、ウィメンズサイズ 9）が発売されたら、100 ドル以下で買って」といった依頼を試せます。

ユーザーが参加する場合との主な違いは、次のとおりです。

* **購入条件の確認**：エージェントは、購入すべきだと理解した内容をユーザーに伝え直す必要があります。
  ユーザーはその内容を承認し、不在時にエージェントが購入を進めることに同意する必要があります。
  ユーザーは、生体認証などのセッション内認証を行い、自分の意思を確認します。
* **Checkout Mandate の状態**：ユーザーが署名する Checkout Mandate に、Shopping Agent が注文を成立させられる条件を記録します。
  Shopping Agent がユーザーの要望を満たす商品や条件を探している間、Mandate は Open の状態です。
  Shopping Agent がすべての条件を満たせると判断したら、Mandate は Closed になります。
* **Merchant による再確認の要求**：Merchant がユーザーの要望どおりに注文を満たせるか確信を持てない場合（たとえば、依頼で特定の SKU が指定されていない場合）、ユーザーにセッションへ戻ってもらい、購入条件の確認や追加情報の入力を求めることができます。
